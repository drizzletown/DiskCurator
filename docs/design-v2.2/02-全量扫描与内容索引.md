# 02 全量扫描、SHA-256 内容索引与性能

## 1. 一次完整扫描

```text
选择根目录 → 递归枚举目录/普通文件 → 获取大小与修改时间
          → 对所有可读取普通文件逐字节计算 SHA-256（含零字节文件）
          → 再次验证文件大小/mtime 未变化 → 写入本地可重建索引
          → 利用 SHA256+大小分桶 → 逐字节验证疑似完全相同内容
          → 后续目录关联、结构建议和融合计划共享同一 Inventory
```

扫描出错者记录 `UNREADABLE/CHANGED/SKIPPED`，不应被默默排除或当作普通内容。目录 junction/reparse point 不跟随。用户可取消全量扫描；取消时不得留下可冒充完整索引的结果。

## 2. 索引记录

当前 `File` 增加 `sha256`；`scan_hashed()` 生成所有可读普通文件的 SHA-256。索引写到 Windows `%LOCALAPPDATA%\DiskCurator\Cache`，其他系统使用 `$XDG_CACHE_HOME/DiskCurator` 或 `~/.cache/DiskCurator`。缓存记录：文件相对路径、文件大小、mtime 原始计数、SHA-256；根路径经哈希生成索引文件名。路径采用 UTF-8 字节的十六进制编码，避免换行、制表符与中文导致格式破坏。

**关键边界**：当前实现**每次主扫描都会重新读取全部文件计算 SHA-256，并重写索引**；并没有实现“可信文件未改变就直接跳过”的热缓存命中方案。持久索引已可用于查阅/导出和后续索引工程，但还未被作为再次扫描时的可信替代物。任何索引被删除不影响用户数据。

## 3. 内容核验

- 同一 SHA-256 与大小表示**重复候选**；精确重复分组使用真实 `equal_bytes`，比对完整文件的内容。
- 逐字节复核（默认）在隔离前和暂存后将被隔离源与每个保留文件再次比较。
- 用户可选择 SHA 快速模式：要求完整扫描哈希以及相关源/保留者大小、mtime 不变，不再执行这两轮内容读取。此模式不能发现大小/mtime 被恢复或伪造的内容更改，必须明确警告。
- 文件身份与副本路径证据只在当前扫描根目录有效；不能得出独立硬盘备份结论。

## 4. 性能优化原则

用户明确要求**先全量扫描并记录哈希**，因此不能再把“只做元数据扫描作为首次扫描完成”的结果冒充完整索引。性能重点转向：顺序磁盘读取、按卷控制并发、读取缓冲、无重复全文件指纹计算、稳定的进度与可取消，以及未来可验证的持久缓存增量命中。

- 全量 SHA-256 首次扫描 I/O 下限近似等于全部可读取文件字节数；1 TB 数据在 100 MB/s 理想顺序吞吐下仅数据读取就约需 2.8 小时，目录寻道与 USB 延迟会延长。
- 对每个重复候选仍需确认精确内容；不能为了速度宣称仅哈希就等同于逐字节无损证明。
- 当前全文件 SHA-256 为 C++17 内部实现，不依赖 Qt 或 OpenSSL。扫描和执行不能共用一份可随外部修改而过期的身份声明。
- 当前 index TSV 不包含设备稳定 ID、增量目录监控或数据库事务；这些属于下一步需要质量验收的优化。

## 5. 后续性能改进（目标，不标记为已实现）

1. 为索引加入卷 ID / 文件 ID、索引代际、错误状态和严格缓存失效规则。
2. 有证据地跳过未变化文件的重复哈希计算，提供“强制重新计算全部哈希”选项。
3. 索引存储改为受控数据库以支持百万文件，但不能把数据库当成用户资料备份或事务执行日志。
4. 单独测量扫描枚举、哈希吞吐、重复确认、目录候选、计划/执行，记录设备和缓存冷热状态。
5. 目录扫描存在失败时明确显示不完整，不能产生无依据的相同目录事实。
