# DiskCurator 需求与总体设计基线 v2.1

**冻结日期**：2026-11-18  
**设计性质**：对功能体系、交互体系和安全契约的正式统一基线；**不是软件 v2.0 发布声明**。  
**源代码参照**：`DiskCurator Native v1.0-rc8` 基础能力候选源码（从 rc7 衍生；Windows 尚未重新验收）  
**前一设计基线**：需求与总体设计 v1.2；UI 设计 v1.3。  
**适用范围**：由用户选择的单根目录，Windows 本地文件系统；可位于移动硬盘，但不做跨根目录/跨设备索引。

## 1. 产品唯一定位

**DiskCurator 是面向混乱历史数据的、由用户主导的本地文件整理决策与安全执行工具。**

用户不需要知道有哪些算法和菜单。用户说“这批资料整理一下”，软件应该：发现资料构成与关系 → 提供可解释的完整新结构 → 允许拒绝或修改 → 展示实际文件影响 → 安全建立整理结果 → 验证并说明旧资料是否可清退。

**本软件优先解决“整理之后更清楚、更完整、可追溯”，而不承诺立即节省空间。** 拷贝后旧目录不动；隔离不等于物理空间释放。

## 2. 一条主线、三种入口、五个业务能力域

```text
用户目标：把一个混乱根目录整理清楚
                   │
        ┌──────────┼───────────┐
        ▼          ▼           ▼
   智能整理(默认)  主题工具       基础工具
   少决策/按步走   按业务任务组合   精细控制与取证
        └──────────┼───────────┘
                   ▼
   [盘点] → [关系证据] → [整理建议] → [执行方案] → [安全复核]
                   │
      同一套 C++17 领域核心与受保护执行器
```

**五个业务域（不等于五个顶层按钮）**：

| 业务域 | 含义 | 成果 |
|---|---|---|
| A 目录盘点 | 识别现状、容量及扫描异常 | 完整清单、目录空间报告 |
| B 内容关系 | 识别精确相同、目录重合、历史变化及照片相似候选 | 有证据的关系图/差异列表 |
| C 智能规划 | 依据 A/B 提出合并与全局目录结构 | 可编辑的新树、完整旧→新映射 |
| D 整理实施 | 复制融合、整体新结构构建、改名和规则归档 | 执行计划与验证后的结果 |
| E 数据保护 | 双副本清退约束、隔离、日志、恢复、审计 | 可解释的风险和操作历史 |

**三种入口**：L1 基础工具是能够独立完成任务的人工操作工作台；L2 主题工具组合 L1；L3 智能整理（默认六阶段）编排 L1/L2。安全执行器共享，不能由高级入口绕过低层安全约束。

## 3. 不可更改的核心决策（ADR）

| ID | 冻结决策 | 理由/约束 |
|---|---|---|
| ADR-01 | C++17 + Windows 10/11 x64 原生 Win32 SDK/Common Controls/WIC | 不引入 Qt、MFC、WebView 或云服务依赖 |
| ADR-02 | 单根目录，所有受控写操作限制在根内 | 不证明另一硬盘/网络上的备份情况 |
| ADR-03 | 精确同内容必须完整逐字节确认 | 文件名、日期、哈希、dHash 都不是最终证明 |
| ADR-04 | 扫描、比较、推荐、编辑建议和生成预览全部只读 | 用户拒绝后不得留下目标文件或事务工作区 |
| ADR-05 | 整体整理分阶段：先构建/校验新结构，再单独申请旧目录清退 | “迁移”不暗含删除原资料 |
| ADR-06 | 不覆盖已有不同内容文件；同名异内容保留两个版本 | 不凭文件名/时间选择“正确版本” |
| ADR-07 | 清退后至少两份独立、活动、已验证的普通文件对象 | 不计硬链接同一对象、隔离区及不可读文件 |
| ADR-08 | 隔离≠永久删除、也不等于释放空间 | 当前版本不提供自动永久删除 |
| ADR-09 | 故障时显式报告部分完成，禁止虚构全局原子性 | 已完成并验证的复制结果可以保留 |
| ADR-10 | 危险判定在核心执行器，不依靠 GUI 控件禁用状态 | 三层入口不能绕过安全不变量 |
| ADR-11 | 智能建议必须提供证据与不确定项 | 用户可拒绝/改映射/改方向；不自动实施 |
| ADR-12 | 版本状态严格区分源码实现、特定环境测试和发布资格 | `PASS / FAIL / NOT RUN / BLOCKED` 并存档证据 |

## 4. 产品边界与明确排除

**纳入**：指定单根目录扫描，P0–P2 现有单目录需求；内容去重、目录等价/差异/包含、推荐融合、目录结构建议、文件级例外、两阶段整理、重命名、归档、照片相似人工审核、受约束隔离与撤销。

**不纳入当前正式发布能力**：跨盘扫描索引、多盘副本安全证明、自动永久删除或空间回收、云同步、自动删除相似照片、照片语义人物识别、自由拖放任意嵌套树及比较多个规划方案、未经真实设备测试的突然断电完全恢复保证。

## 5. 基线的使用方法

1. 需求变更先更新 `01`、`02` 和 `10` 中的编号与状态；业务规则以 `04/06` 为准。
2. 任何界面改动都必须引用业务任务与状态，不能新建独立文件操作逻辑。
3. 任何执行能力必须追溯到 `REQ/BR → 领域 API → 测试 Gate`。
4. 原项目的历史文档保留归档，不再把旧版本片段直接当作最新规范。
5. 若源码与本基线不符，记录为 **差距**，不得因为“设计写了”就声称“功能已经完成”。

## 7. v2.1 基础能力优先决策（本节优先于旧文本中的“基础层仅查看证据”的叙述）

- **ADR-13 基础层必须可独立执行。** L1 不只展示信息；重复文件人工选择、重复目录清退申请、相似目录主动发现、任意两个指定目录的评估与融合应形成独立闭环。L2/L3 不得替基础层发明另一套判定算法。
- **ADR-14 相似事实与融合推荐严格分离。** `find_overlapping_dirs` 的候选是内容重合证据，`evaluate_directory_pair` 的报告是事实，`recommend_merges` 才是带启发规则的推荐；三者不可互相代替。
- **ADR-15 手动不等于危险。** 对于任何人工选择的隔离对象，整个计划的最终保留者须有两个独立且内容经逐字节核验的活动文件对象；目录安全清退还须保留者位于被清退范围之外。
- **ADR-16 功能成熟度按三个标记公布。** 已有 API 和通过 Linux 核心测试、写有 Win32 界面代码、Windows 手工与端到端验收，必须分别记录。

本基线以 `12/13/14` 三份基础能力专章作为基础层规范性要求；老章节若只有“基础视图”表述，应以此处新定义为准。
