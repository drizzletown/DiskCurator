本章以 2026-11-20 的 Native 1.0.1 源码为审查对象。本轮只修改文档；下列“待补”条目没有通过文字修订变为已实现。

## 1. 当前源码已具备的主线

| 能力 | 状态与边界 |
|---|---|
| 明确选盘和指定目录 | 默认选盘模式、零预选；只扫描用户确定的根 |
| 完整 SHA 与只读观察 | 主扫描读取普通文件完整内容，保存可重建索引；观察不再读原内容 |
| 全宽结果工作区 | 左侧旧模式、目录树和旧选项卡不再创建；操作按基础/主题/智能分类 |
| 分阶段进度 | 原生进度条、字节/文件量、速率、当前盘阶段 ETA、当前路径、错误和停滞提示；汇总内部仍无百分比 |
| 候选计划 | 所选重复文件、全根多余副本、目录外保留者清退按用户配置生成计划 |
| A/B 范围分析 | 内容读取限子树；当前仍要求原根库存完整，融合限单根不相交子目录 |
| 按需分析与映射 | 精确核验、目录关系、照片、融合建议、结构规则和文件映射由用户明确发起 |
| 计划与执行分离 | 冻结路径、参数及适用策略；同名冲突与快照变化按类型检查 |
| 写后结果过期 | 包括失败和异常；不自动整根重扫，保留只读参考和历史 |
| 分类型恢复 | MOVE 与 COPY 恢复语义不同；普通 Undo 不是全部事务和内容版本恢复 |

当前“智能”能力由本地规则、内容关系和可编辑映射组成，不依赖云模型，也不自动执行建议。界面已有实现不等于原生 Windows 交互和实盘已验收。

## 3. 当前明确保留的能力边界

以下边界应在界面和文档说明，不因本轮列出就承诺立即新增：

- 当前永久删除未实现；隔离不释放空间。用户手动管理唯一文件的需求与是否引入永久删除是不同问题，应分别设计。
- 跨盘可以观察，但跨根写事务未实现，不能把跨盘候选组直接用于现有单根融合。
- COPY 产生的副本不由普通 Undo 自动删除；移动 Undo 不保存内容历史版本。恢复完整文件内容需要额外版本数据，不能仅靠反向路径实现。
- 写事务不提供任意时刻取消；要增加取消，必须明确暂存、提交和恢复边界。
- 目录关系和智能建议有规模与证据约束；显示有限候选不能包装成穷尽结论。
- 主扫描仍完整读取全部符合规则的文件；未来增量模式必须明确不同保证，不能悄悄取代用户要求的完整扫描。

## 4. 收敛次序

先补齐 G-01/G-02/G-04 的口径和反馈，并完成 G-03 的 Windows 验收，使用户能看懂当前结果和当前任务。之后依据真实移动盘测量确认主要耗时落点，再选择增量刷新、续扫或大库存查询等工作。

G-05～G-07 不宜通过一个“缓存命中”开关草率完成。应先定义持久会话、变更证据、错误/过期传播、查询与导出集合，再实现、再加入受控数据和实际介质验收。每一步都保留可明确发起的完整扫描。

基础管理扩展 G-08～G-10 应复用现有证据等级和计划执行器；不能为了让按钮可用而忽略错误、扩展范围或篡改冻结策略。
