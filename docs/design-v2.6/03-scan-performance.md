# 03 — 扫描、进度与性能架构

文档基线：v2.6  
对应实现：DiskCurator Native v1.0.1  
核对日期：2026-11-20

本章规定扫描的范围、内容读取、进度语义、性能边界和测量方法。文中的“已实现”表示能够在当前源码中定位该行为；Windows 原生运行是否通过，须另看当前发布验收记录。源码审查、Linux 回归、交叉编译、真实移动硬盘实测不能互相替代。

## 1. 产品约束与需求编号

| 编号 | 设计要求 | v1.0.1 状态 |
|---|---|---|
| SCAN-01 | 扫描前由用户明确选择一个或多个磁盘，或一个目录；不默认选择、遍历所有磁盘 | 已实现；默认选盘模式没有勾选项 |
| SCAN-02 | 对范围内所有能够读取且状态稳定的普通文件计算完整 SHA-256，包含内容独有的文件和空文件 | 已实现；不以抽样或历史大小/时间相同替代本次读取 |

| PERF-01 | 首次扫描只读取一遍稳定普通文件的完整内容，不默认追加全范围精确比较、照片解码或智能推荐 | 已实现于 GUI 首扫；旧 CLI 的部分命令仍主动执行精确分析 |
| PERF-02 | 进度发布与 UI 消费限流，保留最新状态，避免每个读取块堆积一条窗口消息 | 已实现；核心约 100 ms 发布，UI 约 250 ms 消费 |
| PERF-03 | 移动机械硬盘以顺序读取、资源复用和减少重复 I/O 为基础；不盲目增加竞争读取线程 | 已实现；当前所选根之间也串行扫描 |
| PERF-04 | 目录汇总和观察统计避免逐目录重遍历全部文件及无界字符串复制 | 已实现；仍保留完整库存，内存占用随规模增长 |
| PERF-05 | A/B 内容核验限于两棵选定子树；进入已扫描单盘或切换视角复用已有库存 | 已实现；全范围分析需明确发起 |
| PERF-06 | 小范围文件操作不触发隐式全范围重算哈希；旧结果必须明确失效 | 已实现；可信增量刷新未实现，后续操作需显式重扫 |
| PERF-07 | 吞吐、CPU、枚举、汇总和内存分别测量，性能结论附环境、数据集及误差边界 | 已有诊断工具和 Linux 微基准；Windows HDD 实测未完成 |

## 2. 扫描范围与覆盖声明

### 2.1 两种范围，统一内容扫描

“选择磁盘扫描”由用户先选择 C:、D:、F: 等盘符对应的卷，再开始任务；“指定目录扫描”由用户选择一个目录。两种入口最终采用相同的完整哈希流程。多根输入必须规范化，拒绝重复根以及父子重叠的根，避免重复计数和同一对象进入多个扫描范围。[S1][S2]

磁盘入口在任务前后核对卷身份。盘符仍为 F: 不代表仍是同一个移动硬盘。失联或身份改变应保留异常证据，不能将旧库存用于当前卷的写操作；此规则和操作计划的一致性检查共同生效。[S3]

### 2.2 “完整”针对明确范围内可处理的普通文件

扫描枚举普通文件和目录，记录相对路径、大小、修改时间及错误。对取得有效元数据的文件逐个尝试完整读取；空文件也建立 SHA-256。扫描不会跟随符号链接或重解析点，不将设备或其他特殊对象当普通资料读取。应用拥有的事务工作区与哈希缓存不参加资料盘点；直接把缓存或其子目录选为扫描根会被拒绝。[S1][S2]

因此，对外应分别说明：

- **范围**：用户选择了哪些卷或目录。
- **已盘点集合**：成功取得有效元数据的普通文件与目录。
- **内容已读集合**：完成本次完整哈希且扫描前后状态检查通过的文件。
- **异常集合**：无法枚举、读取失败、状态改变、重解析点跳过及其他不支持对象。

发现异常时，不能把已盘点集合当作范围内全部真实对象。文件大小为 1 TB 的磁盘标签也不是读取进度的分母。

### 2.3 首扫与按需分析的边界

首次扫描交付哈希库存、文件候选组、目录候选签名和多视角观察；不自动开始全范围逐字节去重、照片解码、目录关系分析或智能推荐。手动 A/B 评估与融合预览仅构造两棵子树的临时分析库存。明确请求全范围精确核验或智能分析时，界面先说明任务范围，再进入相应后台任务。[S2][S3][S4]

从候选生成隔离预览，不等于强制预先核验整盘。执行前的实际内容复核、保留份数和独立性服从用户选定策略；对应操作规则见操作计划设计。

## 3. 处理流水线与模块职责

| 步骤 | 输入与输出 | 主要内容 I/O | 实现位置 |
|---|---|---|---|
| 范围冻结与校验 | 用户选择 → 本次任务根集合 | 卷与目录元数据 | Win32 入口、`scan_roots_hashed` |
| 枚举与目录汇总 | 根 → `Inventory` 文件/目录、大小、时间、异常 | 目录及文件元数据，不读取整份内容 | `core.cpp::scan` |
| 完整 SHA-256 | 文件元数据 → 哈希或读取异常 | 每个稳定普通文件一次完整读取 | `hash_index.cpp::scan_hashed` |
| 保存索引 | 内存库存 → 可重建缓存 | 写应用缓存 | `save_index` |
| 跨根候选分组 | 各根库存 → 大小＋SHA 候选组 | 无用户内容读取 | `scan_roots_hashed` |
| 观察统计 | 库存 → 文件副本候选数、目录大小与树候选数 | 无用户内容读取 | `observations.cpp::observe_scan` |
| 结果展示 | 库存及观察 → 当前视角 | 无隐式重新读盘 | `win_main.cpp` |
| 显式精确或主题分析 | 已选对象/范围 → 分析结果或计划 | 仅该任务需要的读取 | `deduplicate`、`scoped_analysis.cpp` 等 |

核心某个根发出的 `Complete` 事件表示该核心阶段完成；GUI 仍须等待后续候选分组和观察统计结束。多根任务也不能在第一个根结束时显示全任务完成。[S2][S3]

当前保存索引发生在单根哈希完成之后，再进入下一根。所选根按顺序处理，没有同时启动多个磁盘读线程的自动调度器。

## 4. 进度数据契约

`ScanProgress` 是独立于日志文字的只读状态快照。[S5]

| 字段 | 语义与使用限制 |
|---|---|
| `phase` | `Enumerating / Hashing / Verifying / SavingIndex / Analyzing / Complete` |
| `root`、`current_file` | 当前根及正在处理的对象；无当前文件时可显示阶段说明 |
| `files_discovered` | 当前根已枚举的文件数；枚举结束前持续增加 |
| `files_completed` | 当前阶段已处理的文件尝试数，包含失败尝试；不是成功哈希数 |
| `total_bytes` | 当前根已枚举文件的逻辑大小之和；可能包含随后读取失败的文件 |
| `bytes_read` | 哈希/核验读取循环实际返回并计入处理的内容字节；不同于物理磁盘流量 |
| `bytes_processed` | 已核销的工作量；哈希失败文件未读的剩余工作量在记录错误时核销 |
| `errors` | 当前阶段记录的读取/处理异常计数；必须与完成比例共同呈现 |
| `root_index / root_count` | 当前根的序号与所选根数，序号从 1 开始 |
| `totals_known` | 当前阶段是否已有可用于进度比例的总量；未知时显示活动条 |
| `elapsed_seconds` | 多根入口提供整个多根任务累计时间；GUI 的已用时间也以本任务计时 |

**进度条达到 100% 只表示本阶段待处理工作均已处理，不等于每个文件都读取成功。** 例如某 10 GiB 文件只读入 1 GiB 后失败，实际读取量增加 1 GiB，而处理工作量最终核销 10 GiB；错误必须同时保留。界面应显示“扫描结束，存在读取异常，结果不完整”，不显示“所有内容均成功验证”。[S2][S3][S5]

读取异常的哈希留空，不能参加有效哈希组。观察层目前无法从字符串错误可靠判断精确受影响的子树，因此某根有扫描错误时，该根目录副本数统一按未知处理；成功取得的文件哈希仍可只读观察。这里的目录候选数 0 表示证据不足，不应解释为“确定没有副本”。[S4]

### 4.1 分阶段呈现

- **枚举**：文件数、已发现容量、当前路径、已用时间；不估算未知总量的百分比或剩余时间。
- **哈希**：以字节工作量计算比例，同时显示文件数、实际读取速率、异常数和当前文件。空文件或尾部大量小文件以文件完成量辅助，避免字节已读完却长期停在“100%”。
- **保存索引、候选分组、观察统计**：显示具体阶段与活动条。目前未提供这些阶段内部的可靠百分比。
- **精确字节核验**：候选可能因哈希碰撞拆组，比较次数与最终读取量事先不确定；显示实际读取字节和文件处理量，不伪造总字节分母。
- **取消/异常**：说明本次任务未完成；新的未完成扫描不能替换为可执行结果。

### 4.2 速率和 ETA

GUI 基于内容读取字节增量计算近期速率，阶段或根变化时重置统计。当前实现每约 750 ms 更新速度估计，并用历史速度与新样本平滑；没有进展或样本不足时显示“估算中”。ETA 同时考虑剩余字节与剩余文件，取可用估算中的较大值，以覆盖零字节文件与小文件打开开销。[S3]

多磁盘任务明确显示“磁盘 i / n”。当前百分比与 ETA 仅属于当前盘阶段；全任务已用时间累计。未枚举后续磁盘时，不承诺整个多盘任务的准确剩余时间。

达到约 15 秒无新的文件或读取进展时，界面显示等待提示并停止给出看似可靠的 ETA。该提示帮助识别停滞，不自动诊断坏盘、USB 故障或程序死锁，也不自动跳过对象。

## 5. 后台任务、取消与资源开销

扫描、比较与只读分析由后台线程运行。核心通常约每 100 ms 发布快照，阶段边界、首个内容块和最终状态立即发布；GUI 约每 250 ms 读取互斥保护的最新快照。进度采用覆盖最新状态的方式，不给每个 I/O 块分配并排队一个窗口消息。[S1][S2][S3]

完整哈希在每个 1 MiB 读取块之间检查取消；精确比较在两路 256 KiB 缓冲读取之间检查取消。枚举、分组、观察统计和索引写出也设置取消检查。取消不直接中断或释放仍在使用的文件句柄；必须由工作线程正常退出后回收资源。[S1][S2][S4]

当前 Windows 文件读取使用同步系统调用。如果设备失联导致一次 `ReadFile` 长时间不返回，用户点击停止后仍需等该调用返回。文档和界面不得保证异常设备上的“立即停止”。也不能把只读扫描的可取消性推广为文件提交阶段可任意中断。

不同计划任务的取消粒度也不相同：`StructurePlan` 当前不可中途取消；部分隔离、清退和重命名计划器只在返回后处理取消标志，不能保证所有预览构造都具有块内停止能力。

文件操作后不再自动重算整个根的 SHA-256。结果进入过期状态，保留查看、导出及历史；新分析或写入需显式重新扫描。该行为避免一次小操作触发隐式数小时读盘，但不等同于已经实现增量刷新。[S3]

## 6. I/O 与算法设计

### 6.1 内容读取

Windows 使用 CNG SHA-256：算法提供者在进程内复用，单次根扫描复用哈希对象和 1 MiB 读取缓冲区；采用顺序访问提示与 Unicode 长路径处理。文件打开后检查普通磁盘文件属性，拒绝叶节点重解析点；读取前后核对大小、修改时间等，变动文件不产生有效扫描哈希。[S2]

不声明每台 CPU 必然启用某一种硬件加速，也不承诺固定提速倍数。可移植实现仍用于非 Windows 平台和文本签名；它直接处理完整 SHA 数据块，避免不必要的输入复制。Windows 与可移植实现均应通过相同已知向量测试。

当前以单流读取一个根中的文件，避免多个线程在同一机械盘上竞争寻道；多个所选根也按顺序处理。此策略是明确的当前边界，尚未实现物理磁盘拓扑识别、SSD/HDD 自适应并发或每盘独立调度。

### 6.2 目录和观察统计

目录大小与文件数先累积到直属目录，再按由深到浅的顺序合并到父目录。保留排序和路径索引开销，但不对每个祖先重复遍历每个文件。[S1]

文件副本候选统计借用库存中的哈希字符串视图，避免为每个文件再长期复制一份完整哈希字符串。目录观察用节点索引组织父子关系，预计算深度；只为当前目录生成签名载荷，再统一分配签名组编号。结果库存不可在观察函数执行中被并发修改。[S4]

结构建议的顶层分类改为一次文件聚合，不再为每个顶层目录扫描全部文件。全目录关系或智能推荐仍是另行发起的分析，不能把首次观察统计的低耗时当作所有高级分析的性能证据。

### 6.3 内存与显示限制

当前库存、候选组和观察索引保存在内存中，规模随文件和目录数量增加；目录树还有排序、索引和当前签名编码的临时开销。本版不是数据库分页库存，也不是固定内存的流式全盘索引。

结果列表最多构造一定数量的展示行，常用文件/目录视角为 5000 条；完整库存继续保留，筛选在完整库存上进行，再截取显示。显示上限只约束 UI 行构建，不能用来承诺总内存固定或扫描规模无限。[S3]

## 7. 内容索引持久化与未实现能力

Windows 缓存位于 `%LOCALAPPDATA%\DiskCurator\Cache`，每根的索引以规范化根路径派生文件名。索引记录根、完整/部分状态、文件相对路径、大小、修改时间和 SHA-256；文件名和路径字段采用现有 v1 编码格式。[S2]

写出使用独立临时文件。完成后替换目标缓存；失败或取消时清理本次临时文件。缓存可以重建，不是操作日志，也不是恢复点。缓存保存失败时，已完成的内存哈希仍可观察，必须告知“索引未持久化”，不能反过来宣称文件内容读取失败。

核心通过文本进度回调报告保存告警，不将它写入 `Inventory.errors`。当前 GUI 仅保留最新消息，后续汇总或完成状态可能覆盖该告警，因此持久化失败的持续可见展示仍是实现差距；不能把核心回调已有等同于 GUI 已完整满足上述要求。

下列能力**尚未实现**，不得写成 v1.0.1 的既有特性：

1. 根据可信变化证据在下次扫描跳过未变文件的完整读取。
2. 中断后恢复未完成扫描或从大文件中间续算。
3. USN/MFT 驱动的文件变化追踪，以及跨次缓存恢复所需的卷身份映射与缓存重绑定；当前任务前后的卷身份核对已存在，不能等同于跨会话恢复。
4. 文件操作后只更新受影响对象的可信增量刷新。
5. 基于物理磁盘拓扑和介质类型的并发读调度。
6. 用数据库或外部排序支撑超大库存的有界内存处理。

后续若实现这些能力，需要单独设计变化证据、失效条件、完整性状态、回退全量扫描和验收矩阵。不能仅凭“文件大小和 mtime 相同”将旧哈希冒充本次完整内容读取结果；如另设增量扫描模式，须与完整扫描的保证明确区分。

## 8. 性能预算和验收方法

### 8.1 本基线的约束

| 项目 | 设计约束或测量目标 | 证据边界 |
|---|---|---|
| 首扫内容读取量 | 对稳定、可读、互不重叠的普通文件集合，哈希循环累计内容量应等于这些文件大小之和；无隐式第二轮精确比较 | 可用计数和受控数据集验证，不等于物理设备只读了同样字节 |
| 范围操作 | A/B 分析不得因其他目录体积大而读取其内容 | 已有无关离线文件回归；测试中的 TiB 元数据不是实盘 |
| 进度发布 | 正常处理期间按约 100 ms / 250 ms 的发布/消费节奏更新；变化频繁时不堆积窗口消息 | 是实现节奏，不是所有系统负载下的刷新时延保证 |
| 取消 | 大文件内部及长循环检查取消；不要求等待整个文件处理完成 | 同步 OS I/O 阻塞时间不在立即响应保证内 |
| 计算开销 | 枚举、哈希、索引、候选分组、观察分别计时；禁止用整体时间掩盖某阶段回归 | Windows 与实际移动硬盘还需采样 |
| 内存 | 同一库存下记录峰值与临时分配，增长应可解释；观察优化不得以丢失文件或目录换取数字改善 | 目前有 50 万文件纯内存对照，无全平台容量上限声明 |
| 完成判据 | 覆盖错误数、成功哈希数、目录未知状态与取消状态；不单凭进度条或平均速度验收 | 正确性优先于单一吞吐指标 |

不为“1 TB 磁盘”设定没有文件分布和设备条件的固定完成时限。基准应同时报告实际待读字节、文件数、目录数、大小分布、介质与连接方式、平台、编译配置及缓存状态。

### 8.2 分层数据集

- **内容正确性与边界**：空文件、SHA 标准向量、55/56/63/64/65 字节填充边界、跨 1 MiB 缓冲区、百万个 `a`、扫描中变更、文件消失、取消、多根编号。
- **纯库存规模**：1 万、10 万、50 万文件记录，深目录、大量平级目录及重复树；只测候选和观察统计，标明不读实际文件内容。
- **真实存储吞吐**：分别测少量大文件、大量小文件、混合备份目录；同机同盘交替运行旧新版本，记录冷/热缓存条件，至少多次报告中位数和波动范围。
- **设备与异常**：在可丢弃数据上观察只读错误、文件占用和移动盘断开，记录等待、停止、错误与部分库存表现，不将受控失败计入正常吞吐均值。
- **端到端任务**：首扫到结果可用、进入单盘、A/B 评估、隔离预览、操作后失效与显式重扫，检查是否出现未授权的额外全范围读取。

数值阈值应依据指定 Windows 测试机和真实 HDD/SSD 基线另行签署。当前文档没有把未执行的 Windows 性能目标登记为已通过。

### 8.3 诊断工具

`dc_benchmark ROOT --scan` 测量实际完整哈希加观察路径，输出 TSV：

- `scan_enumeration`：枚举及目录汇总。
- `scan_sha256`：完整内容读取与 SHA-256。
- `scan_save_index`：缓存保存。
- `scan_hash_groups`：跨根哈希候选分组。
- `scan_full_sha256_total`：扫描主流程总计。
- `build_observations`：只读观察统计。

诊断包含阶段耗时、进程逻辑读取量、峰值内存和 `content_read_bytes`。进程逻辑读取量受系统缓存影响，不等于物理 USB 传输量。默认模式仅盘点元数据；`--full` 保留旧的精确去重诊断含义，不等同于 GUI 的首次扫描。[S6]

先选择具有代表性的小目录，避免为了诊断再隐式读取整个大盘。示例：

```powershell
.\build-win\Release\dc_benchmark.exe "F:\照片样本" --scan > scan-profile.tsv
```

该命令确实读取指定目录的全部普通文件内容，并写出可重建应用缓存；它不改动样本资料。

## 9. 当前性能证据

### 9.1 纯内存观察统计

数据集为 500,000 个文件、10,001 个目录，其中 10,000 个同构顶层子树、每子树 50 个文件。Debian 13 x86_64、GCC 14.2、`-std=c++17 -O2`；旧新二进制使用相同的旧版可移植 SHA 文本签名后端，隔离观察算法变化的影响。三轮交替结果见 [E1]。

| 指标 | 旧版中位数 | 新版中位数 | 可支持的结论 |
|---|---:|---:|---|
| 观察计算时间 | 0.738192 s | 0.474773 s | 此计算约减少 35.7% |
| 进程峰值 RSS | 271,384 KiB | 188,680 KiB | 此进程峰值约减少 30.5% |

峰值包含输入库存和整个进程；共享主机 CPU 负载会影响时间。没有测量 Windows CNG、实际移动硬盘或 1 TB 文件读取。

### 9.2 完整哈希微基准

Linux、GCC 14.2、`-std=c++17 -O2 -pthread`、可移植 SHA、操作系统缓存未清空；旧版 hotfix1 与新扫描五轮交替比较，记录见 [E2]。

| 数据集 | 旧版中位数 | 新版中位数 | 可支持的结论 |
|---|---:|---:|---|
| 20,000 个 257 字节文件，共 5,140,000 字节 | 0.481405 s | 0.404526 s | 此微基准约减少 15.97% |
| 单个 64 MiB 文件，共 67,108,864 字节 | 0.235850 s | 0.240510 s | 新值约高 1.98%，不支持宣称大文件提速 |

不能把这些时间当作实际机械盘的读取速度。Windows CNG 的吞吐和实际 UI 体验仍需 Windows 运行证据。

### 9.3 对“1 TB 扫描一晚”的解释范围

代码审计确认旧手动目录及进入单盘管理的部分流程曾在完整 SHA 后继续进行全部候选精确比较和建议生成。一个稳定重复组有 n 份、每份 S 字节时，仅哈希需读取 nS；若随后逐一与代表文件比较，比较阶段可再读取 2(n−1)S。新 GUI 将这些按需分析从首扫中拆出。[H1]

旧的“所选磁盘”首次扫描原本就是一次完整哈希，没有这段自动比较。不能仅凭磁盘容量和等待时间，认定用户那次扫描的瓶颈一定来自重复读盘，也不能据此断定磁盘故障。

作为纯算术示例，若实际待读为 1,000,000,000,000 字节，以持续有效的 100 MB/s、50 MB/s、20 MB/s 读取，仅内容读取分别约为 2 小时 47 分、5 小时 33 分、13 小时 53 分，尚未加入枚举、打开文件、哈希 CPU 和汇总开销。这里采用十进制 MB/s；这是容量/吞吐估算，不是产品性能承诺。

应通过新进度与诊断记录判定时间落在哪一阶段，再针对读盘、文件打开、CPU、统计或异常重试采取措施。
